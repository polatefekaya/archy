# Source inventory and C# syntax analysis

`archy inventory` creates a deterministic, workspace-scoped inventory before any source facts are trusted. It walks only repository-relative paths, excludes Git metadata, Archy-managed state, generated `bin`/`obj` output, symbolic links, configured exclusions, and `.gitignore` rules. It hashes raw file bytes with SHA-256 and stores only path, language, hash, length, and observation time in local SQLite state—never source content.

The inventory is transactional as a cache update: an incomplete scan reports diagnostics and does not add, change, or delete cache rows. A later complete scan compares the current files with the cached snapshot and reports deterministic Added, Changed, Deleted, and Unchanged results. CLI JSON uses named enum values, not implementation integers.

`archy analyze` is the first graph-producing pipeline:

1. Synchronize the source inventory.
2. Skip only when that inventory is unchanged and an active graph revision already exists.
3. Start a durable analysis run for a revision-producing analysis.
4. Parse the complete C# inventory with Roslyn syntax trees, verify each source hash still matches the inventory snapshot, and emit file, declaration, unresolved-using-reference, declaration-edge, symbol, and public-surface fingerprint facts.
5. Commit the complete fact snapshot through the immutable graph-revision transaction.

Syntax errors produce structured diagnostics and mark the analysis incomplete. The corresponding run is recorded as failed and no graph revision is activated. A source file that changes after inventory is a conflict rather than a potentially stale graph commit.

Each revision-producing run records `git rev-parse --verify HEAD` when that commit is available. An unborn or otherwise unresolvable `HEAD` is explicitly stored as absent; Archy never invents provenance.

The C# syntax provider deliberately records only syntactic evidence. `using` targets are `unresolved_reference` nodes at 0.65 confidence; generic LSP semantic symbols, references, and outgoing calls are collected separately through declarative profiles, while framework pattern providers remain separate future providers. This distinction keeps static facts honest and preserves a clean Native-AOT host boundary for any later bounded sidecar capability.

The first framework provider is explicit .NET dependency injection registration. It matches only generic `AddScoped<TService, TImplementation>`, `AddSingleton<TService, TImplementation>`, and `AddTransient<TService, TImplementation>` calls. The provider emits a `di_registration` edge from the service declaration to the implementation declaration only when each simple type name maps to exactly one syntax declaration in the snapshot. The registration lifetime is part of the normalized join key, so two lifetimes do not collapse into one fact. Missing or ambiguous declarations remain diagnostics, never guessed edges.

The companion DI consumption provider recognizes normal and primary-constructor parameters. It emits a `di_consumes` edge from the consumer type to a uniquely resolved source-defined service only when the service has at least one supported explicit registration. A missing registration produces an `unregistered_constructor_dependency` diagnostic and no edge. Multiple distinct implementations retain the consumer-to-service fact and all registration facts, while adding an `ambiguous_di_registration` diagnostic; Archy never selects one implementation.

Recognized assembly-scanning registrations—currently Scrutor-shaped `Scan(...)` chains and Autofac-shaped `RegisterAssemblyTypes(...)` calls—are reported as `unsupported_di_registration_pattern` diagnostics. They intentionally produce no registration edge because a Native-AOT syntax provider cannot truthfully reconstruct reflection-selected types. The `analyze` CLI prints provider diagnostic counts and records, and its JSON form returns the same structured diagnostics.

The .NET configuration-read provider creates first-class virtual `configuration_key` nodes. It records static indexer reads, `GetValue`, section binding (`Bind` and `Get`), and `Environment.GetEnvironmentVariable` calls rooted in the conservative syntax shapes `configuration`, `config`, or `*.Configuration`. Key paths are normalized with `:` separators; environment `__` separators join the same logical key space. Each `configuration_read` edge includes both its access form and normalized key path, with source evidence. Dynamic keys emit `dynamic_configuration_key` and produce no guessed node or edge. The provider is intentionally syntax-only until semantic C# facts can prove arbitrary `IConfiguration` receiver types.

The JSON definition provider currently supports repository `appsettings*.json` documents, including comments and trailing commas accepted by the .NET configuration format. Each document is a `configuration_file` node; every static object property and array position becomes a `configuration_defines` edge to the normalized virtual key, with a JSON Pointer and one-based source location in its evidence. Defined-but-unread keys remain in the graph. Read keys with no JSON definition report either `missing_configuration_definition` or `environment_only_configuration_key`; duplicate paths inside one JSON document and malformed documents are reported rather than resolved heuristically. Additional JSON file conventions and non-JSON providers remain explicit future adapters.

The raw RabbitMQ provider recognizes literal `BasicPublish`, `QueueBind`, and `BasicConsume` calls. It models a `message_exchange` and `message_queue` resource graph as `producer → exchange → queue → consumer`, using `rabbitmq_publish`, `rabbitmq_route`, and `rabbitmq_consume` edges respectively. The empty exchange literal is canonicalized as `amq.default`; raw values remain in evidence. All required exchange, queue, and routing-key arguments must be static strings. Any dynamic or incomplete route is reported as `dynamic_rabbitmq_route` and yields no topology fact; connection/client type resolution, asynchronous overloads, declarations, and broker-observed topology remain separate future providers.

The typed .NET messaging provider is likewise explicit and syntax-only. It connects an enclosing declaration (or, when there is none, the source file) that invokes `Publish<TMessage>` or `Send<TMessage>` to each source-defined declaration explicitly implementing `IConsumer<TMessage>`. `message_publish` and `message_send` are deliberately distinct edge kinds, while the message type is the normalized join key. It accepts qualified consumer contracts such as `MassTransit.IConsumer<TMessage>`, but creates no edge unless both the message declaration and participating consumer declaration resolve unambiguously in the current snapshot. Missing, duplicate, or non-source declarations become deterministic diagnostics.
